# 측정 세션 — desktop-13900kf / 2026-09-15

## 무엇을 쟀나

- 항목 : M7. GetAllActorsOfClass
- 조건 : N = 10 / 100 / 1,000 / 10,000 · mode = disabled, once, everytick, cached, foreach · 반복 5
- 실행 명령 :

```
python tools/run_bench.py --scenario getallactors --machine-id desktop-13900kf ^
  --mode disabled,once,everytick,cached,foreach --n 10,100,1000,10000 --repeats 5 ^
  --warmup-sec 3 --measure-sec 10 --profile cpu --affinity FFFF ^
  --engine "C:\Program Files\Epic Games\UE_5.8\Engine\Binaries\Win64\UnrealEditor-Cmd.exe"
```

`--profile cpu` 만 돌렸다. `both` 이 기본이지만 이 항목은 `full` 이 필요 없다.
재려는 일이 전부 `Scenario->RunFrame` 안에서 일어나고 러너가 그 구간을
`FPlatformTime::Seconds()` 로 직접 재므로, 주 지표 `scenario_ms` 는 `-nullrhi` 에서도
살아 있다. 프로토콜 3.3 의 M7 행도 `-nullrhi` 기본 사용이다.

  측정 직전 전체 CPU 부하는 3초 평균 **3.5%** 였다
- 전원 계획 : 고성능 (`8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c`)
- 코어 고정 (`--affinity`) : `FFFF` — P코어 논리 0–15
- 측정 중 자리를 비웠나 : 해당 없음 (원격 세션, 사람 입력 없음)

## 실행 중 눈에 띈 것

### 이 세션은 M1 과 두 가지 조건이 다르다

| | M1 (2026-08-23) | M7 (이 세션) |
|---|---|---|
| 엔진 | `5.8.1-56057345` | **`5.8.2-56702186`** |
| 주 GPU (env.json 기록값) | `NVIDIA GeForce RTX 4060 Ti` | **`Parsec Virtual Display Adapter`** |

엔진 버전이 올라간 것은 이 세션이 만든 변경이 아니다. 런처가 갱신한 결과이고,
00-plan 5장이 "엔진 버전이 바뀌면 머신이 바뀐 것과 같이 취급한다" 고 못박아 두었으므로
**M7 수치를 M1 표에 올리면 안 된다.** 항목이 다르므로 당장 섞일 일은 없지만,
나중에 머신별 비교표를 만들 때 걸린다.

GPU 기록값이 Parsec 가상 어댑터로 남는 것은 `-nullrhi` 항목이라 측정에는 영향이 없다.
다만 `env.json` 만 읽는 사람은 이 머신에 실제 GPU 가 없다고 오해할 수 있으므로 여기 적는다.

### 히치 경고에 대해

검증 실행(측정 3초)에서 10개 조건 중 5개가 히치 1% 문턱을 넘었다. 본 스윕(10초)에서도
저부하 arm 은 넘을 것으로 본다. 이것은 이 세션의 문제가 아니라 **지표의 성질**이다.

히치는 "중앙값의 1.5배 초과 프레임" 이므로 프레임이 짧을수록 쉽게 걸린다.
`-nullrhi` 대조군은 0.3ms 로 도는데 1.5배면 0.45ms 이고, 그 정도 흔들림은 어떤 머신에도 있다.
M1 의 채택된 결과도 같은 모양이었다 — `disabled N=10000` 5회가 0.72 / 1.34 / 1.95 / 0.99 / 1.86%
로 전부 경고를 받았고, `tick N=10000` 은 228fps(4.4ms)라 0.09% 였다.

그래서 M1 리포트는 히치를 실격 사유로 쓰지 않고 **분포에 대한 데이터로 본문에 표로 실었다.**
타이머의 33.83% 는 그 자체가 결론이었다. M7 도 같은 방식으로 다룬다. 숨기지 않고 싣는다.

- 중간에 끊기거나 다시 돌린 실행 : 없다. 100회가 한 번에 끝났다 (exit 0)
- 조건을 바꿨다면 무엇을, 왜 : 프로토콜 조건은 바꾸지 않았다

그 교란은 주 지표를 흔들지 않았다. `everytick N=10,000` 5회의 `scenario_ms` 는

`cached` 는 r3 가 오히려 가장 낮다. 같은 실행의 `frame_ms` 는 0.8028 → 0.8870 으로 7% 올랐다.
히치는 프레임 수준에 얹혔고 시나리오 구간 자체는 안정적이었다.

## 판단

- 이 세션 결과를 리포트에 쓸 수 있나 : **쓸 수 있다.** 근거는 위 표와 아래 두 가지다.
  - 히치 경고는 실격 사유가 아니다. 이 프로젝트는 M1 에서 이미 같은 판단을 했다.
    `disabled N=10000` 5회가 0.72–1.95% 로 전부 경고를 받았지만 리포트는 그것을 숨기지 않고
    본문 표로 실었고, 타이머의 33.83% 는 그 자체가 결론이었다. 히치는 "중앙값의 1.5배 초과"
    라 프레임이 짧을수록 쉽게 걸린다. `-nullrhi` 대조군은 0.3ms 로 도니 1.5배가 0.45ms 다
  - 이 세션의 주 지표는 `scenario_ms` 이고, 위에서 보인 대로 히치가 그 지표를 흔들지 않았다
- 쓸 수 없다면 이유와 다음에 바꿀 것 : 해당 없음

### 남는 숙제

1. **엔진 5.8.2 와 5.8.1 이 섞였다.** M1 은 5.8.1, M7 은 5.8.2 다. 같은 표에 올리지 않는
   것으로 당장은 충분하지만, 머신별·항목별 비교표를 만들 때는 M1 을 5.8.2 로 재측정할지
   결정해야 한다. 이건 사람이 정할 문제다
2. **Parsec 세션이 붙은 채로 쟀다.** 부하는 3.5% 로 작고 `-nullrhi` 라 렌더 경합도 없지만,
   M1 은 로컬 디스플레이 상태에서 쟀다. 같은 항목을 로컬에서 다시 재서 차이가 없다는 것을
   확인해두면 이 기록이 필요 없어진다
3. **`make_report.py` 의 신호 바닥이 이 지표에 맞지 않는다.** `signal_floor()` 가
   `max(측정한 바닥, 0.02)` 이라 상수가 이기는데, 프로토콜 4장과 그 함수 자신의 주석은 둘 다
   측정한 바닥이 이겨야 한다고 적혀 있다. `scenario_ms` 는 `game_ms` 보다 약 100배 정밀해서
   여기서 처음 물렸고, 12개 조합이 "신호 없음" 으로 떨어졌다. 고치면 M1 의 발표된 표도
   바뀌므로 손대지 않았다. 사람이 정할 문제다
4. **원인 분석 패스를 아직 돌리지 않았다.** `GetAllActorsOfClass` 가 `ForEachObjectOfClass`
   보다 액터당 10배 비싼 이유는 Insights `cpu` 채널로 봐야 한다 (프로토콜 5.4, 별도 실행)
