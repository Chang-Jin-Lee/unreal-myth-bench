# unreal-myth-bench

언리얼에서 오래 돌아다니는 성능 통설 아홉 개를 실측으로 검증하는 벤치마크 하네스입니다.
산출물은 데모 장면이 아니라 다른 사람이 클론해서 같은 숫자를 뽑을 수 있는 리포트입니다.

**현재 상태 — 계획 단계.** 기획 문서와 측정 프로토콜만 있습니다. UE 프로젝트는 아직 없습니다.

## 무엇을 재나

| | 통설 | 실제로 재는 것 |
|---|---|---|
| M1 | Tick을 쓰지 마라 | 등록된 Tick 수와 작업량에 따른 게임 스레드 시간, Tick Group별 총비용 |
| M2 | Blueprint Event Tick이 비싸다 | Lyra에서 CMC · PlayerController · BP Tick 스코프의 프레임당 시간 |
| M3 | Blueprint는 C++보다 느리다 | VM 경유 횟수별 격차, Development와 Shipping 양쪽 |
| M4 | Cast를 쓰면 다 로드된다 | 런타임 비용과 에셋 로드 의존성을 분리 측정 |
| M5 | Cast와 Implements는 성능이 같다 | 호출당 비용과 참조 그래프 차이 |
| M6 | ChildActorComponent를 쓰지 마라 | 배치 수·생성 빈도에 따른 스폰 시간과 메모리 |
| M7 | GetAllActorsOfClass는 느리다 | 액터 수 축과 호출 빈도 축 중 어느 쪽이 지배적인지 |
| M8 | 정확한 주기는 TimerManager로 | 실행 간격 분포와 deadline 초과율 |
| M9 | Paper2D는 죽은 기능이다 | 5.8 기준 지원 범위 조사와 드로우콜 |

측정 항목은 2026 언리얼 페스트 "언리얼 엔진의 모범 사례에 대한 오해와 진실" 트랙을 들으며
직접 던진 질문에서 나왔습니다. 강연 결론을 받아 적는 대신 각 주장이 어떤 조건에서 참이 되는지를
곡선으로 남기는 것이 목적입니다.

공통 스윕 축은 `N = 10 / 100 / 1,000 / 10,000`입니다. 단일 수치가 아니라 곡선을 남깁니다.
통설은 대부분 특정 구간에서만 참이기 때문입니다.

## 구조

```
docs/       기획 문서와 측정 프로토콜, 항목별 결과 리포트
MythBench/  UE 5.8 프로젝트 (예정)
tools/      헤드리스 실행 · 파싱 · 리포트 생성 (예정)
results/    머신별 · 날짜별 원시 결과
```

측정 결과는 `results/<machine-id>/<date>/`에 머신별로 나눠 담습니다.
CPU가 다르면 곡선의 절대값이 통째로 이동하므로, 한 그래프에 두 머신의 점을 찍지 않습니다.

Lyra와 실제 프로덕션 프로젝트는 측정 대상이지만 코드와 에셋을 이 레포에 넣지 않습니다.
재현 절차와 숫자만 문서로 들어옵니다.

## 재현

프로젝트가 만들어지면 여기에 명령어를 채웁니다.
리뷰어가 직접 돌려볼 수 있다는 것이 이 프로젝트의 신뢰도 전부입니다.

## 환경

Unreal Engine 5.8 · Windows · Visual Studio 2022 · Python 3.11+

가상 머신에서는 측정하지 않습니다. CPU 토폴로지가 가상화되고 호스트 스케줄러가 개입해
프레임 시간 분산이 커집니다.
